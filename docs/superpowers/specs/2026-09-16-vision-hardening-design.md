# 视觉识别稳定化设计

日期：2026-09-16
范围：实施方案第 2 步中可在无真实方舟凭据条件下完成的工程工作

## 目标

在保留现有 FastAPI、原生前端、SQLite 和同步请求流程的前提下，加强图片入口、视觉模型输出和结果保存，使错误图片、超限图片、非法模型输出、网络异常和空隐患结果都有明确且可测试的行为。

本阶段完成：

- 前端图片预览、长边压缩和 JPEG 转换；
- 后端上传体积、真实图片内容、格式和像素尺寸校验；
- 视觉输出的严格结构验证；
- 总体时间预算以及 JSON/结构错误的有限修正请求；
- 网络、超时、供应商和输出错误分类；
- 图片质量、不确定项和总结的持久化；
- 无隐患结果保持空数组，不创建假隐患；
- 报告页展示图片质量、总结、不确定项和空状态；
- 对应自动化测试和文档更新。

真实模型效果、真实网络行为和 10 张现场图片验收依赖团队提供凭据及合规样本，本阶段只建立手工验收入口并明确保留待办。规章检索、风险分级、整改建议、后台任务和分步骤进度不在本阶段实现。

## 方案选择

采用“后端强校验 + 前端体验增强”的增量方案。浏览器处理减少手机上传耗时，但所有安全与完整性约束仍由后端执行，不能信任前端结果。

未采用只做后端的方案，因为它不能满足移动端预览和压缩要求。未采用完整工作流重构，因为后台任务与分步骤状态属于实施方案第 4 步，提前实现会扩大范围并增加回归风险。

## 配置

在集中配置中增加：

- `MAX_UPLOAD_BYTES`：默认 `10485760`，即 10 MiB；
- `MAX_IMAGE_PIXELS`：默认 `25000000`，限制解码后的总像素数；
- `VISION_REQUEST_TIMEOUT_SECONDS`：单次供应商请求超时，默认 30 秒；
- `VISION_TOTAL_TIMEOUT_SECONDS`：一次视觉分析含修正请求的总预算，默认 75 秒；
- `VISION_JSON_RETRIES`：JSON 或结构错误后的修正次数，默认 2，限制在 0–2。

配置值必须为正数，总体预算不得小于单次请求超时。`.env.example` 和 README 同步说明默认值。

## 图片上传与处理

### 前端

上传页增加独立 JavaScript 文件，避免继续扩大内联脚本。用户选择文件后：

1. 检查浏览器可读取的图片类型；
2. 解码图片并显示预览；
3. 若长边超过 1600px，按比例缩小；否则保持原尺寸；
4. 通过 Canvas 转为质量约 0.85 的 JPEG Blob；
5. 显示原始大小、处理后大小和最终尺寸；
6. 提交时用处理后的 Blob 替换表单图片，文件名使用 `.jpg`；
7. 解码或压缩失败时阻止提交并给出中文提示。

页面仍显示后端返回的最终错误。前端限制只用于体验，不能替代后端验证。

### 后端

新增 `backend/app/utils/images.py`，提供单一图片验证入口。处理顺序：

1. 分块读取，最多读取 `MAX_UPLOAD_BYTES + 1`；超过上限立即拒绝；
2. 使用 Pillow 从内存解码并执行完整校验；
3. 只接受实际格式 JPEG、PNG、WebP；
4. 验证宽高为正且总像素数不超过配置；
5. 使用检测到的格式决定 `.jpg`、`.png` 或 `.webp` 扩展名；
6. 以 UUID 文件名写入上传目录。

声明 MIME 不在允许集合时仍提前拒绝。声明 MIME 与实际格式不一致时返回 HTTP 400，不自动纠正，以减少伪装文件和调用方歧义。

图片过大返回 HTTP 413；内容无效、格式不支持、声明与内容不匹配或像素异常返回 HTTP 400。响应使用稳定中文消息，不包含 Pillow 堆栈或本地路径。若数据库写入前保存文件失败，不创建巡检记录；若保存后数据库创建失败，应删除本次尚未被引用的新文件。

## 视觉输出契约

新增 `backend/app/schemas/inspection.py`：

- `ImageQuality`：`good`、`poor`、`uncertain`；
- `VisualHazard`：`name`、`location`、`evidence`、`confidence`；
- `VisualAnalysis`：`image_quality`、`hazards`、`uncertain_items`、可选 `summary`。

所有模型禁止未声明字段。`name`、`location`、`evidence` 和不确定项去除首尾空白后不得为空；文本设置合理长度上限；`confidence` 必须为数值且处于 0–1。`hazards` 和 `uncertain_items` 必须为数组。模型返回值通过 `VisualAnalysis.model_validate()` 后才可进入业务流程。

提示词同步要求可选 `summary`：对当前照片可见范围给出简短客观总结，不得生成法规、风险等级或整改建议。无隐患时 `hazards` 必须为空。

## 模型请求、重试与错误分类

`VisionClient` 创建 `AsyncOpenAI` 时设置 `max_retries=0`，避免 SDK 重试与业务重试叠加。单次请求使用配置的请求超时，整个分析通过异步总体超时控制。

首次响应按“提取 JSON → JSON 解码 → Pydantic 校验”处理。仅 JSON 解码或结构校验失败时发送修正请求，最多 `VISION_JSON_RETRIES` 次。修正请求携带上一份响应和精简的校验错误，要求只返回符合契约的 JSON；响应文本和错误摘要均设置长度上限。

以下错误不执行 JSON 修正：

- 连接失败：`VisionNetworkError`；
- 单次或总体超时：`VisionTimeoutError`；
- 供应商 HTTP/配额/鉴权错误：`VisionProviderError`；
- 所有修正机会用尽：`VisionOutputError`。

这些异常对外转换为稳定且不含密钥、URL 查询参数、供应商原始正文或堆栈的中文消息。巡检记录仍保存为 `failed`，内部 `error` 字段也只保存经过裁剪的安全消息。

## 数据库兼容迁移

在 `inspections` 表增加：

- `image_quality TEXT`；
- `uncertain_items TEXT NOT NULL DEFAULT '[]'`，保存 JSON 数组；
- `summary TEXT`。

`init_db()` 在建表后读取 `PRAGMA table_info(inspections)`，只对缺失列执行 `ALTER TABLE ADD COLUMN`。迁移可重复运行，不删除或覆盖旧记录。旧记录读取时把空值或无效 JSON 安全转换为空数组。

本阶段不新增版本化迁移框架；每次数据库结构变化仍需先备份。后续字段继续沿用可重复的增量迁移，直至项目需要独立迁移工具。

## 业务保存规则

- 成功视觉结果将 `image_quality`、`uncertain_items` 和 `summary` 写入巡检记录；
- 每个真实隐患继续写入 `hazards`；
- `hazards=[]` 时不写入占位隐患；
- 若模型未提供 `summary`，系统生成不夸大覆盖范围的固定总结；
- 演示模式把配置提示写入巡检 `summary`，不创建假隐患；
- `/api/dashboard` 的隐患数只统计 `hazards` 表中的真实结果，因此新产生的演示和无隐患记录贡献 0；已有旧占位数据不做破坏性自动删除。

列表和详情 API 将 `uncertain_items` 输出为 JSON 数组，而不是数据库中的 JSON 文本。详情中的 `hazards` 始终为数组。

## 页面行为

上传页增加移动端 viewport、图片预览、处理信息、前端失败状态和提交期间禁用按钮，避免重复点击。成功后仍跳转到报告页。

报告页展示：

- 图片质量；
- 当前照片总结；
- 无法确认的项目列表；
- 隐患列表。

无隐患时显示“当前照片可见范围内未发现明确隐患”，同时提醒不能替代完整现场检查。演示模式显示配置提示。新内容必须通过 `textContent` 或 DOM API 渲染，不把模型文本拼接到 `innerHTML`。本阶段修改到的报告渲染应一并消除现有模型文本注入风险。

## API 变化

`POST /api/inspections` 的成功响应保持 `id`、`status`、`mode`，兼容现有页面。新增或明确以下错误：

- HTTP 400：图片内容无效、格式不支持或 MIME 不匹配；
- HTTP 413：上传体积超限；
- HTTP 502：供应商连接、响应状态或输出最终无效；
- HTTP 504：视觉分析超时。

`GET /api/inspections` 和 `GET /api/inspections/{id}` 增加 `image_quality`、`uncertain_items`、`summary`。API 契约同步更新。

## 测试设计

所有测试使用临时数据库、临时上传目录和模型替身，不调用真实付费 API。

最低覆盖：

1. 有效 JPEG、PNG、WebP 通过后端内容验证；
2. 伪图片、截断图片、不支持格式和 MIME 不匹配返回 400；
3. 超过字节或像素限制的图片被拒绝，且不创建数据库记录；
4. 严格模型拒绝缺字段、多余字段、空文本、非法枚举和越界置信度；
5. 合法 JSON、Markdown 代码块 JSON 仍可解析；
6. 首次非法响应经一次修正后成功；
7. 连续三份非法响应后停止，并确认总请求数为 3；
8. 网络、供应商和超时异常不触发 JSON 修正，映射到稳定错误；
9. 图片质量、不确定项和总结保存后可从详情 API 恢复；
10. 无隐患和演示模式不创建 `hazards`，统计数为 0；
11. 旧结构数据库启动后增加缺失列且保留原记录；
12. 页面脚本不使用模型文本构造 `innerHTML`，浏览器手工检查预览、压缩和错误状态。

## 手工验收边界

自动化测试通过后，团队仍需提供：

- 有效方舟 API Key 与支持图片输入的接入点；
- 来源和使用范围明确的 10 张现场图片，覆盖清晰隐患、无明显隐患、模糊/遮挡和多隐患；
- 可接受的请求配额和网络环境。

手工验收记录模型标识、每张图片的状态、结构校验结果、失败分类和总耗时，不记录密钥或私人照片副本。准确率结论留到独立标注评测阶段，不用模型自报置信度替代。

## 验收标准

- 后端不接受伪造、超限或格式不匹配的图片；
- 前端可预览并将长边压到不超过 1600px 后上传；
- 模型数据只有通过严格契约后才能入库；
- JSON/结构修正最多两次，网络和超时不误重试；
- 图片质量、不确定项和总结刷新后不丢失；
- 无隐患与演示模式不会增加隐患数；
- 旧数据库可增量升级且数据保留；
- 报告页不直接用 `innerHTML` 渲染模型文本；
- 自动化测试不访问真实模型、不污染 `data/`；
- 未取得凭据和样本时，文档明确标记真实模型与 10 图验收未完成。
