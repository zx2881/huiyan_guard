# 慧眼安巡项目实施方案

更新：2026-09-16。本文件是当前开发顺序、范围和验收的唯一执行依据；原始产品方案保留为立项参考。

**硬目标：9 月 28 日前基本完成，能随时参加校赛。**按用户确认的实际需要，9 月 23 日冻结主要功能，9 月 26 日完成软件与材料，9 月 27 日完成模拟演示。10 月的赛事提交窗口只用于正式提交及必要修订，不作为开发缓冲。若校赛通知更早，则以更早日期倒排。

## 一 这次要交付什么

交付一个可以在电脑和手机浏览器使用的校园安全巡检 Web 系统。核心场景先做宿舍，用户上传照片后得到有照片证据、风险等级、真实规章出处和可执行整改建议的报告；用户可以确认、纠正或补充 AI 结果，报告保存后可再次打开和打印。分析过程能看见，失败有明确提示。

核心流程：

```text
选择宿舍场景 → 上传照片 → 图片校验
  → 视觉识别 → 检索真实条款 → 风险分级 → 整改建议
  → AI 内部复核（达到主链路验收后加入）
  → 展示结果 → 人工确认/修改/补录 → 保存与打印报告
```

| 必须完成 | 条件允许再做 | 本次暂缓 |
| --- | --- | --- |
| 上传、真实视觉分析、真实规章检索、风险分级、整改建议 | AI 内部复核，最多重做一次 | 整改照片提交、现场复查与销项 |
| 人工确认/修改/补录、进度、历史记录、完整报告与打印 | 历史记录筛选、两三项基础统计 | 完整实验室知识库、统计大屏、知识库后台 |
| 公网演示、明确标识的离线回放、评测与校赛材料 | 实验室清单切换演示，明确能力边界 | 向量数据库、原生 App、实时视频、复杂组织权限 |

这是根据现有工程与剩余时间制定的执行范围。保留已有的实验室清单和页面入口，但缺乏对应条款时不能展示为已完成专业分析。AI 内部复核只是审查报告，不代表现场隐患已经消除。

## 二 从已有成果继续做

已有：FastAPI 入口，原生 HTML/JS 三个页面，SQLite 三张表，稳定图片上传与视觉结果契约、历史查询、基础报告、基础统计接口、方舟视觉客户端、宿舍 10 项与实验室 1 项清单，以及 25 条宿舍公共法规和幂等导入/检索模块。

未完成：真实视觉/文本模型验收、本校公寓制度、公网部署、内部 AI 复核和参赛材料。人工确认、可追溯修改、补录、移动端报告与打印已经实现。当前规则分级、建议和法规检索已经串入后台工作流，但不能替代真实模型与现场验收。详见 [当前进展](02_当前进展.md)。

继续使用现有 FastAPI + 原生 HTML/JS + SQLite；先保留 `sqlite3`，不在本轮迁移 ORM。条款量小，先做关键词和同义词检索；单进程部署，进程内后台执行，状态写数据库，前端轮询。新增文件随功能建立，避免先复制一棵空目录树。

## 三 八步实施

每一步只有验收通过才能标为完成；“代码写了”“页面能打开”不能代替端到端结果。后端、前端、资料和部署可按下述依赖并行，角色可由同一人兼任。

### 第 1 步 固定开发基线与接口

**时间：9/16–9/17。负责：后端、前端、队长。**

**工程状态（2026-09-17）：已实现并通过 13 项自动化测试与 Uvicorn 启动验收。**已完成集中配置、数据库连接关闭、应用工厂、健康检查、API 契约、隔离测试和 README 同步。真实方舟账号/接入点、文本模型选型、报名与设计文档正文仍需团队提供外部信息或推进，不计作代码已完成。

1. 按代码仓库 README 在独立虚拟环境安装依赖，启动现有原型，保存可复现的依赖版本。
2. 完成真实方舟账号与接入点配置；确认一个文本模型的供应商、模型名、版本和配额。密钥仅写本机 `.env` 或服务器环境变量，不进入方案或 Git。
3. 将环境配置集中到 `backend/app/config.py`；数据库/图片路径应实际读取配置，补 `/api/health`。
4. 约定巡检、隐患、条款引用、进度和人工修改字段，写入开发时新建的 `huiyan_guard/docs/api.md`。
5. 队长同步推进盖章报名、成员信息与校赛通知；材料负责人按官方模板起草设计文档，不等功能全做完再开始。

**产物：**干净环境启动记录、接口约定、模型登记、设计文档提纲。**验收：**另一名队员照 README 能启动，健康接口返回成功；前后端对必填字段和状态枚举无歧义。

### 第 2 步 把视觉识别做稳

**时间：9/17–9/18。负责：后端/AI，前端配合。依赖：第 1 步。**

**工程状态（2026-09-17）：已实现并通过 38 项自动化测试。**图片预览压缩、后端真实内容校验、统一结构校验、方舟有限修正、超时/错误分类、兼容迁移、无隐患零计数和报告安全渲染已完成。真实方舟/YOLO 推理效果与 10 张现场图片验收仍待凭据、权重和样本，不标记为完整业务验收。

1. 前端增加图片预览、格式和大小提示，压缩长边至不超过 1600px 并转 JPEG；后端再次校验实际图片内容，限制上传体积（建议 10MB，可配置），不能只信 MIME。
2. 为视觉输出增加严格结构校验：隐患名称、位置、可见证据、置信度范围、图片质量、不确定项；拒绝错误字段类型。
3. 区分网络错误与 JSON 格式错误；后者最多追加 2 次修正请求，设置总体时间预算，避免与 SDK 重试叠加导致长时间等待。
4. 保存 `image_quality`、`uncertain_items`；未发现隐患时保持隐患数组为空，把总结存在巡检记录里，不创建假隐患。
5. 用 10 张实际图片验证，至少包含清晰隐患、无明显隐患、模糊/遮挡和多隐患图片。这里检验链路与失败处理，准确率由后面的独立标注评测给出。

**视觉模型边界：**当前方舟适配器和未来 YOLO 适配器都必须向业务层返回同一份结构化结果。YOLO 的权重加载、类别/检测框映射和推理超时处理只放在 `yolo_client.py`；不把 YOLO SDK、类别 ID 或检测框泄漏到路由、报告、规章检索和人工确认层。接入详情见 [YOLO 接入预留](yolo-接入预留.md)。

**主要位置：**`integrations/vision_provider.py`、`integrations/vision_factory.py`、`integrations/vision_client.py`、`integrations/yolo_client.py`、`perceive.py`、`schemas/inspection.py`、`utils/images.py`、上传页。

**验收：**真实模型返回内容能够校验与保存；坏图片、非法 JSON、超时都有明确结果；无隐患不增加隐患数；不确定项刷新报告后仍存在。

### 第 3 步 建立可用的规章知识库

**时间：9/17–9/19，与第 2 步并行。负责：知识库/材料、后端。**

**工程状态（2026-09-17）：公共法规基线已实现，当前总计 51 项自动化测试通过。**宿舍清单扩展为 10 个可见检查项，整理 25 条带稳定 ID、官方来源、核验日期、关键词和检查项映射的法规记录；幂等导入、数据库兼容迁移和场景/关键词/同义词检索已完成。用户所在学校及校内公寓制度尚未明确，因此校级规则仍待团队补充，实验室法规仍按计划暂缓。

1. 明确适用学校与宿舍场景，先围绕已有的插线板覆盖、通道堵塞检查项找真实文件，再扩展约 6–10 个有视觉证据的检查项。
2. 整理约 20–30 条适用条款作为目标规模；条数不够时先确保核心场景有准确依据，不用泛化条款填数量。每条含 ID、文件名、条号、原文、来源链接、核验日期、适用场景和关键词。
3. 写入 `knowledge/dormitory/regulations.json`，在 `knowledge/sources/README.md` 记录来源；这与“检查清单”是两类数据，不能混用。
4. 新建 `scripts/import_knowledge.py`，校验后按稳定 ID 更新 SQLite；重复导入不产生重复条款。
5. 新建 `backend/app/knowledge/retriever.py`，按场景过滤、隐患关键词/同义词打分，返回若干最相关条款；无匹配返回空，不能回填任意条款。

**验收：**核心隐患能找到人工核对过的相关条款；无关场景和无依据输入不误配；同一文件导入两次数量不增加；任一引用能打开或定位原文。

### 第 4 步 串起分级 建议与真实进度

**时间：9/19–9/20。负责：后端/AI。依赖：第 2、3 步。**

**工程状态（2026-09-17）：后台主链路已实现。**上传后返回 202 和巡检编号，后台依次更新视觉识别、规章检索、风险分级、整改建议和完成状态；报告页轮询真实进度。条款引用按当次结果保存快照，失败可重试，服务重启会把遗留任务标记为中断。未配置文本模型时使用透明规则模式，无条款时转待人工核验。真实视觉/文本模型端到端效果仍待凭据和样图验收。

1. 新建文本模型客户端、分级和建议模块。团队先定义内部风险等级（建议低/中/高），附判定依据；无充分证据时使用“待人工核验”，不把内部等级冒称为法规等级。
2. 分级输入只能包含照片证据和已检索的条款；模型返回条款 ID，后端核验 ID 后附上原文与出处，拒绝虚构引用。
3. 建议输出具体措施、优先级、建议完成时间和需人工核实的内容；区分“建议期限”和条款明确要求的期限。
4. 工作流依次执行感知、检索、分级、建议、保存。`POST /api/inspections` 先返回编号，后台执行；前端每 500–1000ms 查询详情中的实际步骤，完成或失败后停止轮询。
5. 保存当次条款快照；调整知识库后旧报告保持原引用。应用重启时将遗留的执行中任务明确标记为中断并允许重试，不能永久卡在分析中。

**主要位置：**`integrations/text_client.py`、`agents/classify.py`、`agents/remediate.py`、`workflow/runner.py`、巡检接口/服务、数据库迁移。

**9/20 阶段验收：**上传真实宿舍图片，能得到至少一份有真实证据、等级、出处和具体建议的报告；过程显示真实步骤；失败有记录。未通过时，暂停所有加分项，将剩余人力投入主链路。

### 第 5 步 完成人工确认与可交付页面

**时间：9/20–9/22。负责：前端、后端。页面可从第 1 步起按接口约定并行。**

1. 保留上传、历史、报告三个页面，统一导航与样式，补移动端 viewport 和布局；把逐渐增长的脚本拆入 `frontend/assets/js/`。
2. 报告展示照片、质量/不确定项、隐患位置与证据、等级、规章原文与链接、整改建议、人工状态和分析耗时。
3. 新增人工确认、修改、补录接口及表单；保留 AI 原始结论，记录人工修改后的值、操作时间和说明，刷新后仍有效。
4. 报告文字通过安全文本节点或转义渲染；加载、失败、空记录、无隐患、待核验分别显示，避免把模型输出直接拼进 `innerHTML`。
5. 完成打印样式，浏览器打印/保存 PDF 时隐藏操作按钮，照片、条款和正文不截断。修正统计，不计演示提示和无隐患总结。

**验收：**手机完成上传、查看、确认/修改/补录，刷新后结果仍保存；历史报告可再次打开；出处可点击；打印内容完整；错误情况下有继续操作入口。

**工程状态（2026-09-17）：已实现。**新增人工确认、修正、误报和补录接口，保存 AI 原始值与每次操作前后快照；误报从统计中排除。三个页面统一为响应式产品界面，历史记录支持搜索和状态筛选，报告显示分析耗时、图片质量、依据原文、来源链接和人工状态，并提供打印样式。自动化测试覆盖人工操作持久化、审计、统计口径和安全 DOM 渲染；手机实机与纸张打印仍需部署后手工验收。

### 第 6 步 部署 复核与可靠性收尾

**时间：9/18 首部署，9/21–9/23 完成验收。负责：部署/测试、后端。**

1. 9/18 先部署现有原型以排除服务器、网络和持久化问题；主链路接通后更新部署。新建 Dockerfile/启动脚本和部署说明，单个应用进程挂载 `data/`。
2. 完成手机流量下真实巡检；重启服务后原照片和报告仍可读取；验证密钥不进入网页、源码交付包和错误响应。
3. 修复上传限制、连接关闭、异常处理、重复提交与必要的请求限流；演示照片采用可公开样本。若要承载真实校园敏感照片，必须先实现访问控制，不能沿用公开 `/uploads` 目录直接开放。
4. 主链路通过后，于 9/21–9/22 加入 AI 内部复核：检查证据、条款适用性、等级和建议；最多触发一次重做，再不通过则转人工。复核结果入库、前端可见。
5. 9/23 完成一轮集中验收，冻结主要功能。若复核仍不稳定，则关闭该项并同步材料，保留人工确认；之后只修影响演示/交付的问题。

**验收：**外网手机完整走通，重启不丢记录，不出现永久执行中；已启用的复核有明确退出条件；有可回滚版本。多进程、Redis 和复杂集群不在本轮计划内。

### 第 7 步 评测与离线保底

**时间：9/21 开始积累，9/23–9/24 完成。负责：测试/演示、知识库。**

1. 将图片整理到样例/评测目录，记录来源与可用范围；为每张图人工标注可见隐患和不可确认项目。保留未用于调提示词的图片作为验证集。
2. 先有 10 张冒烟样本，再争取约 50 张标注图片。给出实际样本数、误报/漏报、精确率/召回率、请求失败率、端到端耗时中位数和 P95；样本不足要如实说明，不为凑数字随意生成标签。
3. 新建 `scripts/evaluate.py`，输出可复查结果与 `docs/evaluation.md`。端到端耗时以请求提交至报告完成计，不能只记录模型单次请求耗时。
4. 新建 `scripts/seed_demo.py`，准备 3–5 个可离线查看的完整既有报告，包含照片和条款快照；明确标注为历史结果回放。断网时不伪装成实时 AI 分析。
5. 演练模型超时、无条款、模糊图片、无隐患、多隐患、服务重启；保留必要的接口/工作流回归测试，验证真实故障分支，不只断言页面返回 200。

**验收：**评测可重跑、数字可追溯；断网能完整展示既有报告；正常与失败演示都能继续，回放不依赖外部 CDN 或模型 API。

### 第 8 步 材料打包与校赛演练

**时间：9/24–9/26 成稿，9/27 总演练。负责：材料/视频、队长，全员互检。**

1. 作品简介：使用真实软件截图，准备 3 张核心功能图，简介按现有要求控制在 400 字以内，附赛道和联系信息。
2. 设计文档：按 `赛事资料/设计文档模板-2026年.doc` 编写，说明需求、模块、流程、数据、运行步骤、测试结论；登记真实模型名称/版本、工具平台和 AI 辅助编程说明。原始立项方案不能直接代替设计文档。
3. 源码 ZIP：包含运行必需的代码、前端、清单、真实条款和依赖说明；排除 `.git`、`.env`、虚拟环境、运行数据库、私人照片和日志。
4. 安装/部署 ZIP：包含安装启动脚本、配置模板、部署说明、演示数据导入方法。交给未参与开发的人按说明启动，不能只在作者电脑上可用。
5. 视频：先录 4 分钟左右版本，MP4/H264，控制在 5 分钟和 150MB 以内；包含真实上传、分析步骤、依据、人工修正和历史报告，录好后核验编码和播放。
6. 准备 5 分钟讲解、常见问题回答和公网/离线两套演示。9/26 全套材料进入外层 `交付物/`，9/27 从头到尾模拟校赛并留一版稳定包。

**验收：**软件、设计文档、截图和视频的功能表述一致；五类材料齐备可打开；报名/校赛手续有明确状态；9/27 当天可直接参加演示。正式平台提交由队长按实际窗口操作并留存成功凭证。

## 五 分工与协作方式

| 角色 | 拥有的工作 | 每天交接的东西 |
| --- | --- | --- |
| 后端/AI | 模型、检索、工作流、数据库、人工操作接口 | 可运行代码、接口变化、成功/失败样例 |
| 前端 | 上传、进度、报告、人工确认、历史、打印 | 实际页面、联调问题、手机操作结果 |
| 知识库/材料 | 条款核验、清单、标注、设计文档、简介 | 来源齐全的条款、标注、与实现一致的正文 |
| 部署/测试/演示 | 公网、持久化、回归、离线、录屏和打包 | 可访问地址、验收记录、可播放视频和可安装包 |
| 队长 | 校赛/报名节点、任务分配、范围与版本冻结 | 当天阻塞、负责人与完成时间 |

人少时：后端兼部署，资料兼视频，前端兼界面验收。任务状态只记“未开始、进行中、待验收、完成、受阻”；受阻必须写原因、下一步和负责角色。每天以一个可运行版本和验收证据交接，数据库改动先备份并迁移，不删库重建。

推荐按第 1–8 步逐次推进开发，每次只完成一组相关功能并验证，不一次性生成整套空模块。代码仓库 `docs/` 将来只保存 API、评测、设计正文、演示脚本等具体产物，不再复制一份总计划。

## 六 核心数据和接口约定草案

以下是开发起点，尚未实现的字段/接口不得标为现有能力；第 1 步需结合现有数据库确定最终结构。

| 对象 | 至少保存 | 约束 |
| --- | --- | --- |
| 巡检 | 场景、照片、状态、当前步骤、创建/完成时间、图片质量、不确定项、总结、错误、模型信息 | 无隐患也是有效结论；分析完成与人工确认分开 |
| 隐患 | AI 原始值、人工最终值、名称、位置、证据、置信度、等级、建议、人工状态 | 置信度仅代表模型自报，不冒称实测准确率；提示信息不作为隐患 |
| 引用快照 | 条款 ID、文件名、条号、原文、URL、检索时间 | 只引用实际检索到的条款；旧报告不随知识库更新变化 |
| 人工操作 | 巡检/隐患 ID、操作类型、前后值、说明、时间 | 无登录时不能冒称已经验证了操作者身份 |
| 复核 | 结论、问题清单、次数、最终处理 | 最多重做一次，之后进入待人工核验 |

| 接口 | 现状 | 计划用途 |
| --- | --- | --- |
| `POST /api/inspections` | 已实现异步创建 | 返回编号和初始状态，后台执行分析 |
| `GET /api/inspections/{id}` | 已有 | 扩展真实进度、质量、引用、人工状态 |
| `GET /api/inspections` | 已有 | 保留历史，必要时增加状态/日期筛选 |
| `PATCH /api/hazards/{id}` | 待新增 | 修改或确认隐患，记录审计信息 |
| `POST /api/inspections/{id}/hazards` | 待新增 | 人工补录，标记人工来源 |
| `POST /api/inspections/{id}/retry` | 待新增 | 仅允许失败/中断记录重试，防止重复任务 |
| `GET /api/health` | 待新增 | 基础健康检查，不返回密钥和内部错误详情 |

状态建议：`queued → perceiving → retrieving → classifying → remediating → reviewing（可选）→ completed`；任何执行步骤可转 `failed`。人工确认单独使用状态字段，不把“报告完成”写成“现场已整改”。
